На независимом аналитическом примере найден дефект абсолютного времени double:
начало `999999000000 ns`, `P=81`, `H=97`, один поток, чанк 64 KB, загрузка и запись
по 64 KB, compute_units=49, четыре MC-costs по 0.1, без конфликтов. Длительность по формулам
равна `47692000/78570 = 607.000127… ns`. Старый прогноз выдавал следующий запуск
в `999999000607`, хотя первый допустимый целый момент — `999999000608`.

Теперь callback timestamp хранится как uint64_t, события рассчитываются относительно
него, а Completion сохраняет целое начало и дробную относительную длительность.
Округление выполняется до целочисленного сложения. Проверка дедлайна и сравнение
SMT также используют относительные длительности. Задержки или подобранные константы
к расписанию не добавлялись. Предположение об округлении каждой фазы официальным
симулятором не вводилось.

Граница latest_start также хранится как целый дедлайн минус относительная длина
пути. Сравнение целых и дробных частей сохраняет порядок при большом времени
поступления. Добавлены проверки срочной задачи с низким приоритетом, наследования
дедлайна потомка и допуска зависимой задачи при началах 0 и 2^63 ns. Изменение
исправляет представление того же критерия очереди, не меняя порядок критериев.

Проверка текущей версии:

## Исправления после первой отправки, 21 сентября 2026

Пользователь прислал отчёт первой отправки: 19 TLE, один WA, 0 пройденных тестов.
Для WA checker явно сообщил: `thread=0` вне допустимого диапазона `[1,4]`.
Исходная реализация ошибочно использовала внутренний индекс потока как внешний ID.
Локальный replay повторял это допущение и поэтому не обнаруживал ошибку.

Теперь SchedulerDecision содержит `thread_id = internal_thread + 1`. Replay отдельно
проверяет диапазон `1..threads`, затем переводит номер обратно в индекс модели.
Новый прямой тест API проверяет каждое число потоков от 1 до 4 и использование всех
слотов, не обращаясь к ExecutionModel для проверки нумерации.

Отдельно на синтетических данных воспроизведена проблема повторных прогнозов:
10000 независимых одинаковых задач, 20 наборов по 500, 32 ядра по 4 потока,
симбиоз -1, нулевые коэффициенты конфликтов памяти. До исправления первые 8
commit занимали 4.27574 s и выдавали только 128 запусков. После заполнения ядер
планировщик заново проверял каждый одинаковый отказ на всех 32 ядрах.

Теперь одинаковый отказ переиспользуется в пределах одного неизменного состояния
commit. Ключ включает тип, DRAM, загрузку, запись, вычисления и абсолютный дедлайн;
после принятого запуска кэш очищается. Числовые параметры эвристики не менялись.
Новые проверки покрывают разные дедлайны и типы, изменение модели после принятого
запуска и повторный вызов после завершения задачи. Закрытые входные данные не использовались.

Проверка исправленных исходников:

- GCC 16.2.0 на Windows, конкурсные флаги: **20/20** групп, demo **6/6**.
- MSVC 19.42, C++17 /O2 /W4 /WX /EHsc /DNDEBUG: **20/20** групп.
- Полный локальный replay нового сценария: **10000/10000** задач вовремя,
  628 commit, **0.193119 s** GCC и **0.202529 s** MSVC.
- Остальные два сценария по 10000 задач с GCC: **0.073007 s** и **1.72042 s**.
- Текущий лог GCC: `build/gcc/validation.log`; диагностика до исправления:
  `tmp/timeout-investigation/run10000.log`.

Время измерено на локальной машине и включает локальный harness; это не серверный
CPU time. Причина присланных TLE **не установлена**: данный синтетический случай
показывает отдельный дефект производительности. Для множества различных работ
повторные прогнозы ещё могут быть дорогими; общего ограничения на их число нет.
Эта версия впоследствии также получила 19 TLE и один WA, как описано выше.
Linux и официальный evaluator локально не запускались.

Компилятор хранится локально и не входит в конкурсную отправку.


Пример собирается из всех корневых `.cpp`, как при конкурсном сборе исходников;
локальный `runner_example.cpp` предоставляет `main()`. Для тестов отдельно

без дополнительных linker flags и подавления предупреждений.

Результат:

- Обе программы собраны без предупреждений и ошибок; C++ исходники не менялись.
- **17/17** групп тестов прошли.

- Разнообразные 10000 задач: **1.59173 s**, 10152 commit.
- Demo: **6/6**, 8 commit, последнее завершение **9650 ns**.
- Исходный runner: exit code **0**, **5 назначений**, только smoke check API.
- Лог скрипта: `build/gcc/validation.log` (теперь содержит более новый прогон выше).

Времена относятся ко всему локальному harness и не доказывают соблюдение лимита

## Выполненные проверки первого отчёта

17/17 групп прошли:

1. Примеры памяти PDF 3.1–3.4: разные DRAM дают окончания 8500 / 5750 ns,
   общий DRAM — 9450 / 6700 ns; неполные чанки учтены.
2. Пример симбиоза PDF 2.7: окончания 47000 / 57000 ns.
3. Коэффициенты -1, 0, 1 при 1–4 потоках, включая повторяющиеся типы.
4. Независимость чтения и записи памяти.
5. Конфликт одного DRAM между ядрами с разными мощностями MC.
6. Доминирующая задержка SRAM, точное заполнение, отказ при нехватке памяти,
   освобождение после завершения, проверки типов, DRAM и номера потока.
7. Вытеснение и полный рестарт в модели, строгое равенство дедлайну,
   округление wakeup вверх и защита сложения uint64 от переполнения.
8. Несколько поступлений, нетопологический порядок задач, одинаковые job IDs
   в разных наборах, произвольные core/job-set IDs, ожидание записи родителя.
9. Правильное направление priority и наследование срочного дедлайна потомка.
10. Выбор совместимого ядра и суммарный SRAM в планировщике.
11. Использование выгодного SMT, откладывание разрушительного SMT,
    защита дедлайна уже работающей задачи при новом поступлении.
12. Игнорирование запрошенных вызовов, нулевой и исчерпанный бюджет.
13. Параллельный запуск на разных ядрах при ненулевом конфликте DRAM.
14. Пустой DAG, повторный commit без повторного запуска, некорректный DAG,
    отсутствующий тип ядра, невыполнимый дедлайн.
15. Детерминированность и дробные времена событий.
16. 10000 задач, 20 наборов, 32 ядра / 128 потоков, одинаковые работы.
17. 10000 задач, 20 DAG, 32 гетерогенных ядра, 2 DRAM, разные поступления,
    типы, приоритеты, вычисления и объёмы памяти; по 10 цепочек на DAG.

В сохранённом запуске MSVC однородный масштабный сценарий занял **0.086 s**,
разнообразный — **1.974 s** (10149 commit-вызовов). Это wall-clock **всего локального
harness**, включая независимые проверки назначений и replay, а не оценка
официального симулятора. Значения зависят от машины; не являются гарантией TL=10 s.
На первой реализации разнообразный сценарий занимал 18.75 s. После устранения
повторного прогнозирования, лишних callbacks, временных векторов и вложенных
поисков он стал укладываться примерно в 2 s на этой машине. Гиперпараметры по
этому измерению не подбирались; изменения касались структуры вычислений.

## Что эти проверки доказывают и чего не доказывают

Численные проверки имеют независимые ожидаемые ответы из PDF. Локальный harness
отдельно проверяет известность и уникальность задач, поступления, завершение
всех родителей, идентификаторы ядер, текущее время старта и приём назначения
моделью ресурсов. Для времени replay используется тот же execution_model,
поэтому интеграционные тесты не являются независимым полным симулятором.

Нет подтверждения совпадения исправленной версии с официальным checker,
измерения пикового RSS или прогона GCC/Linux. Первая отправка не прошла тесты;
результат исправленной версии на сервере неизвестен. Нет поиска
оптимального расписания и доказательства отсутствия всех пропусков дедлайнов.
