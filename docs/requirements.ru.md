# Разбор ТЗ: Symbiotic Jobs Scheduling Problem

Источник: `d:/fisica/statements-260914.pdf`, 70 страниц. Несмотря на имя файла,
внутри находится версия **1.1 от 17 сентября 2026**, changelog на с. 66.
Ниже требования конкурсного решения, а не инструкции для инструментов разработки.

## 1. Что требуется сдать

Нужно реализовать онлайн-планировщик на C++17, наследник `arena::IScheduler`,
и фабрику `arena::create_scheduler()` (с. 4, 44–50). Организатор предоставляет
runner и оценочный симулятор. Собственный симулятор необязателен, но интерфейс
не возвращает фактический прогресс задач, поэтому нужна хотя бы внутренняя модель.

Это алгоритмическая библиотека, а не веб-приложение, UI или парсер формата входа.
Заранее известна конфигурация оборудования, но неизвестны будущие job sets.

## 2. Контракт API

- `set_system_spec(spec)` — один раз после создания, сохранить конфигурацию.
- `arrive_at(time, new_job_sets)` — зарегистрировать поступившие DAG; вернуть
  желаемое время дополнительного `commit_until` в наносекундах.
- `commit_until(time)` — текущий момент симуляции, вернуть вектор решений и
  желаемое время следующего вызова. Название не означает разрешение планировать
  произвольные действия в прошлом.
- `terminate()` — очистка после завершения.
- Решение: `(job_set_id, job_id, core_id, thread_id, start_time_ns)`.
  Идентификаторы job set и job положительные; job_id=0 означает вытеснение
  без замены. job_set_id при этом игнорируется.
- Замена задачи на занятом потоке прерывает старую попытку. Перенос уже запущенной
  задачи требует прерывания и новой попытки. Для ещё не начавшегося решения PDF
  описывает отзыв, но отдельного API отзыва нет: в MVP решения стартуют только сейчас.
- Ранние вызовы ограничены `scheduling_budget`, обновляющимся на каждом
  гарантированном вызове. Runner может не удовлетворить запрос; корректность
  состояния не должна зависеть от того, что запрошенный вызов обязательно состоится.
- Гарантированные вызовы имеют период `scheduling_period` и случайное отклонение
  `gamma_border`. Интерфейс не сообщает, был ли конкретный вызов гарантированным.
- Решения с нарушениями runner может молча отбросить (с. 50). Обратной связи об
  отброшенном решении нет.

## 3. Задачи, зависимости и обязательные ограничения

- Job set — DAG, целиком поступающий в `arrival_ns`, привязанный к одному DRAM.
  Рёбра зависимостей существуют только внутри этого job set.
- Задачу можно запускать после поступления и успешного окончания **всех** родителей.
  Порядок job IDs и порядок задач во входном векторе не обязаны быть топологическими.
- Полный ключ задачи — `(job_set_id, job_id)`.
- Фазы каждой попытки: загрузка, вычисление, запись. Завершение вычислений ещё не
  означает завершение задачи: потомки ждут окончания записи.
- Один поток одновременно занят одной попыткой. Паузы между задачами допустимы,
  между фазами одной попытки — нет.
- Тип задачи должен входить в `allowed_types` ядра, DRAM набора — в `dram_ids`.
- SRAM резервируется сразу на весь объём `load_size_kb + write_size_kb`, до конца
  записи или вытеснения. Ёмкость общая для всех потоков ядра.
- Объём резерва SRAM не округляется до чанков. Округляются объёмы передачи.
- Абсолютный дедлайн = arrival + relative_deadline. Все три фазы должны закончиться
  вовремя. Провал одной задачи проваливает её DAG и **весь тест**, а не только
  priority score. Нельзя отбрасывать задачи с priority=100.
- Приоритет сравнивается по `(priority, absolute_deadline)`; **0 — самый высокий**,
  100 — самый низкий. Это не запрет других эвристик планирования (с. 18).
- Состояния: pending, ready, running, completed, failed.
- Вытеснение разрешено на любой фазе, уничтожает весь прогресс и освобождает SRAM.
  Повторный запуск начинается с загрузки; миграция на другое ядро разрешена.
- Успешное завершение считается по последней непрерванной попытке.
- Первый job set может прийти после нуля.

## 4. Математика времени

Мощности P и H заданы в единицах/микросекунду, интерфейс времени — в наносекундах.
Следовательно, длительности по формулам умножаются на 1000.

Для ядра с размером чанка K:

```
n_load  = ceil(load_size_kb / K)
n_write = ceil(write_size_kb / K)
T_load  = 1000 * n_load  / H * max(c_D_read, c_S_write)
T_comp  = 1000 * compute_units / P
T_write = 1000 * n_write / H * max(c_S_read, c_D_write)
```

Read и write половины передачи идут параллельно: нужен **max, не сумма**.
Нулевой объём записи даёт нулевую длительность. Последний неполный чанк оплачивается
целиком. Пример 3.1 (с. 34) прямо округляет 250 KB до двух чанков по 128 KB.

При k одновременно вычисляющих потоках одного ядра:

```
stretch_compute = k - (k - 1) * symbiosis(core, multiset(types))
rate_compute = P / (1000 * stretch_compute)
```

Симбиоз применяется только к одновременно идущим вычислениям. При k=1 множитель 1
независимо от singleton-значения репозитория. При k=2: s=1 даёт множитель 1,
s=0 — 2, s=-1 — 3. Нужен multiset: одинаковые типы нельзя терять.

Для каждой одновременно идущей передачи отдельно пересчитываются:

```
SRAM same-direction stretch = 1 + (k_core - 1) * alpha
DRAM same-direction stretch = 1 + (k_dram - 1) * beta
chunk_time_load = 1000/H * max(c_D_read * DRAM_read_stretch,
                              c_S_write * SRAM_write_stretch)
chunk_time_write = 1000/H * max(c_S_read * SRAM_read_stretch,
                               c_D_write * DRAM_write_stretch)
```

DRAM общий для подключённых ядер, SRAM локален. Чтение и запись независимы:
Load и Write друг другу не мешают. После перехода любой задачи в новую фазу,
старта, окончания или вытеснения скорости могут измениться. Прогресс внутри
округлённого объёма передачи непрерывный: пример 3.4 использует дробные чанки.

## 5. Размеры входов и среда (с. 40–43)

- 1–32 ядра; 1–4 потока/ядро; 1–4 DRAM.
- SRAM/ядро 128–16384 KB; размер чанка 64–1024 KB.
- P и H: 1–100 units/us; стоимость операции на чанк: 0.0001–100 units.
- alpha и beta: [0,1]; symbiosis: [-1,1].
- 1–50 job sets; 1–500 задач/набор; всего до 10000 задач.
- 1–255 типов; load 1–10000 KB; write 0–10000 KB.
- compute_units 1–10000; priority 0–100; до 100 зависимостей на задачу.
- 10 секунд и 1 GB на тест; одна CPU, без потоковых примитивов.
- Только стандартная библиотека C++17, без сторонних библиотек.
- Каталог отправки плоский: `.cpp`, `.h`, `.hpp`; без подпапок, CMake/Makefile,
  скриптов сборки и конфигов. Локальная разработка и тесты хранятся отдельно.
- Команда организаторов: `g++ -std=c++17 -O2 -Wall -Wextra -Werror -DNDEBUG
  -march=native -o scheduler *.cpp`. Нельзя полагаться на assert для рабочей логики.
- Дополнительные linker flags не предоставляются.

## 6. Оценка (с. 51–65)

20 закрытых тестов. Время расписания T = последняя завершённая задача минус первое
поступление. Нарушение дедлайна/зависимостей/ресурсов, падение, неверный формат,
превышение 10 s/1 GB дают 0 за соответствующий тест.

```
M = max(0, 1 - T / (2 * T_base))
F = sum(((100 - priority_i) / 100) * completion_time_i)
P = max(0, 1 - F / (2 * F_base))
R = 1 - wall_time / 10
test_score = 0.65*M + 0.15*P + 0.20*R
auto_score = sum(q_j * test_score_j), sum(q_j)=1, q_j>0
final_score = 0.8*auto_score + 0.2*expert_score
```

F по формуле (29) использует абсолютное C_i, хотя называется flow time: arrival
из C_i не вычитается. F_base=0 в формуле отдельно не разобран. Baseline не обязан
быть оптимальным. Веса закрытых тестов неизвестны. Отображение scoreboard —
округление score*1e6; во время конкурса показывается auto_score до множителя 0.8.

Экспертиза для top K, обычно 6; остальным expert_score=0. Критерии по 0–10:
модульность, читаемость, корректность модели, качество алгоритма, эффективность,
расширяемость, документация, крайние случаи, проверяемость, чистота C++.
Средняя нормированная оценка по экспертам и критериям. Оценивается финальная
отправка, на scoreboard — последняя успешная. Любое решение/коэффициент надо
уметь объяснить. Дисквалифицированного участника заменяет следующий в рейтинге.

## 7. Ограничения конкурсного runtime / Fair Play

Нельзя: зашивать ответы; эксплуатировать инфраструктуру и побочные каналы;
печатать в stdout/stderr или файлы; подбирать гиперпараметры во время работы;
специализироваться под известный/угадываемый тест; исследовать скрытый входной
формат; обращаться к сети/внешним данным; включать предвычисленные ответы;
исследовать внутренности evaluator, его память/символы, перехватывать checker;
переносить состояние между тестами; измерять checker для распознавания теста;
скрывать нарушения обфускацией; настраиваться по баллам закрытых тестов;
читать или менять переменные окружения. Алгоритм должен воспроизводиться из
исходников и официального входа. Настройки разрешено обосновывать заранее,
а не адаптивно подгонять на скрытом тесте.

Локальный тестовый harness может печатать диагностику и мерить собственное время.
Эта инфраструктура не входит в отправляемую библиотеку. Предоставленный
`runner_example.cpp` печатает результаты; он остаётся локальным примером.

## 8. Расхождения и принятые для MVP допущения

1. В PDF стоимости MC лежат в SystemSpec, в реальном `spec_system.h` — в CoreSpec.
   Используем существующие заголовки без изменения ABI.
2. В ранних листингах PDF arrival/deadline имеют суффикс `_us`; в заголовках `_ns`.
   Доверяем `_ns`; вычисленные из мощности длительности умножаем на 1000.
3. `scheduling_period` в header документирован в us, но `runner_example.cpp`
   шагает тем же числом как ns. Основная модель не зависит от этого периода:
   запрашивает реальные ближайшие события в ns, период и бюджет контролирует runner.
4. Направления MC: по комментариям листинга 2.2 `mc_read_cost_to_sram` = DRAM read,
   `mc_write_cost_to_sram` = SRAM write, `mc_read_cost_to_dram` = SRAM read,
   `mc_write_cost_to_dram` = DRAM write. Имена допускают другое чтение; нужна сверка
   с официальным контрактом, а не догадка по значению в одном тесте.
5. Внешний Thread ID выдаём в диапазоне `1..threads`. Прежнее допущение
   `0..threads-1` оказалось ошибочным: в присланной 21 сентября диагностике checker
   отклонил `thread=0`, указав диапазон `[1,4]`. Внутри ExecutionModel остаются индексы
   `0..threads-1`; Scheduler прибавляет 1 при формировании решения. Core/DRAM IDs
   считаем произвольными, не индексами векторов.
6. Дедлайн: текст говорит «before», также «maximum allowable finish time».
   MVP консервативно требует `finish < deadline`, равенство считает провалом.
7. Гарантированные вызовы: формулы на с. 17 и текст интервалов не вполне согласованы.
   Не воспроизводим генератор jitter внутри планировщика.
8. Запрос вне периода/без бюджета может игнорироваться. API не задаёт явный sentinel
   «не нужен вызов»; используем UINT64_MAX, то есть запрос за пределами периода.
9. В первых формулах памяти нет ceil, но правила и примеры прямо требуют его.
   Округляем число чанков вверх, затем допускаем дробный прогресс.
10. Полного официального runner/simulator и публичного набора тестов в папке нет.
    Локальная модель и её успешные тесты не доказывают совпадение с evaluator.
